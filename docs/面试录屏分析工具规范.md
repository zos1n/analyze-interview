# 面试录屏分析工具规范（v2.1，工具化）

> 由《面试录屏最低成本分析执行方案》（历史实战首次执行）演化而来。
> 原方案保留为历史存档；本规范是可复用工具的唯一执行依据。
> 首次执行实录与全部踩坑记录见产物目录 `execution-log.txt`。
> v2.1（2026-09-01）：预检 httpx 无 venv 时降级延后补测；venv 改为全机共享（路径见 analyzer-config.yaml）；配置实际外置为同目录 `analyzer-config.yaml`。

## 一、定位

对面试录屏做**全本地、零云端费用**的转写与分析：

```text
授权与预检（含网络诊断）
→ 环境安装（FFmpeg + mlx-whisper 共享 venv，仅缺失时）
→ 音轨提取（声道独立性自动判定）
→ Whisper Small 全量粗转
→ 转写病理检测与定向修复（新增）
→ 问题索引（密度聚类，超阈值出选项菜单）
→ Whisper Large V3 Turbo 精转
→ 质量校验（抽检 + 术语对照标注）
→ 外部模型逐题分析（可插拔：codex / api / manual）
→ 最终验收（原视频哈希复核）
```

调用方式：全局斜杠命令 `/analyze-interview 视频路径: <绝对路径>`。

两侧入口：Codex `~/.codex/prompts/analyze-interview.md`、Claude Code `~/.claude/commands/analyze-interview.md`。入口文件只做接线（参数解析、授权门、底线），执行语义以本规范 + `analyzer-config.yaml` 为准，不维护副本。

## 二、执行边界

### 输入与授权

- 用户提供录屏绝对路径（可以是目录，工具列出候选文件让用户确认）。
- 执行前必须获得用户对该录屏的明确读取授权（只读；禁止修改源文件；允许在产物目录新建文件；共享 venv 目录在获批安装时例外，见 `analyzer-config.yaml`）。
- 开工前记录原视频基线（size + mtime + SHA256），收工后复核一致。

### 产物目录

```text
<视频所在目录>/<视频文件名去扩展名>_analysis/
├── source-info.json              # 音轨元信息 + 声道分析结论
├── audio-source.flac             # 原始声道副本（保留声道信息）
├── audio-asr.flac                # 16kHz 单声道 ASR 副本
├── transcript-full.json/.srt     # Small 粗转
├── transcript-full-merged.json   # Small 修复合并（原 transcript-full 不覆盖）
├── question-index.md             # 问题索引（主题簇 + 问句事件）
├── transcript-turbo-merged.json  # Turbo 精转合并结果
├── transcript-key.md             # 逐题关键问答稿（分析的唯一输入）
├── codex-analysis-prompt.md      # 分析指令（external analyzer 用）
├── interview-review.md           # 分析产物
├── execution-state.json          # 断点状态
└── execution-log.txt             # 执行日志（版本/revision/排障记录）
```

目录不可写立即停止，不得改换目录。

运行环境不放在产物目录：共享 venv 位置见 `analyzer-config.yaml` 的 `runtime.venv_path`，全机只建一次、跨视频复用。

### 禁止事项（不变）

- 不覆盖、修改、删除原视频；不删除任何中间产物
- 不修改 `.env`、密钥、证书、项目配置
- 不使用云端视频理解 / 云端 ASR / 声纹服务
- 不把完整转写稿交给分析模型
- 不从来源不明的位置下载 FFmpeg 或模型文件

## 三、阶段 0：授权与预检

依次执行（全部只读）：

1. 视频可读、目录可写、磁盘剩余 ≥ 5GB
2. 原视频基线记录（SHA256 较慢，后台跑）
3. **网络连通性矩阵**（各请求一次，记录延迟与状态码）：

| 目标 | 用途 | 检测方式 |
|---|---|---|
| pypi.org | pip 默认源 | curl + venv 内 httpx 双测 |
| pypi.tuna.tsinghua.edu.cn | pip 备选镜像 | curl |
| huggingface.co | 模型默认源 | curl（超时 10s） |
| hf-mirror.com | 模型备选镜像 | curl + venv 内 httpx |

> venv 不存在时（首次执行或共享 venv 被清理）：httpx 检测**延后到阶段 1 安装完成后补测**，结果回填 `network_decisions`；curl 结果照常记录，预检不因 venv 缺失阻塞。历史网络结论（代理端口、HF 直连超时等）仅作排障参考，一律以本次预检实测为准。

4. **代理检测**：
   - `scutil --proxy` 读 macOS 系统代理
   - `urllib.request.getproxies()` 读 Python 侧生效代理
   - 若系统代理已配置但端口不可达 → 判定"失效代理"，后续所有 Python 网络操作加 `NO_PROXY='*'`

**自动决策表**（预检结果 → 执行策略，无需再逐项问用户）：

| 检测结果 | 策略 |
|---|---|
| pypi.org 直连可用（curl+httpx 均通） | pip 直连 |
| 仅 curl 通、httpx 失败 | 判定代理干扰 → `NO_PROXY='*'` 重测；仍失败则用清华镜像 |
| huggingface.co 超时 | `HF_ENDPOINT=https://hf-mirror.com`（教育网官方镜像） |
| 系统代理配置且端口可达 | 走代理 |
| 系统代理配置但端口不可达 | 全程 `NO_PROXY='*'` |

> 首次执行教训：curl 不读 macOS 系统代理而 httpx/urllib 读，导致"curl 正常但 pip 失败"的错位现象。预检必须两种方式都测。

## 四、阶段 1：环境安装（缺依赖时审批）

**审批门触发条件**：FFmpeg 缺失、共享 venv 缺失或 `mlx-whisper` 版本不符，任一成立时把全部缺失项一次性列出等待批准（不拆多次询问）；全部就绪时只读核验并把版本写入 `execution-log.txt`，直接进入阶段 2，不发起审批。

| 项 | 命令 | 下载内容 | 预计占用 |
|---|---|---|---|
| FFmpeg（已装则跳过） | `/opt/homebrew/bin/brew install ffmpeg` | Homebrew 官方 bottles | 0.5-1.5GB |
| 共享 venv + mlx-whisper（已装且版本符则跳过） | `mkdir -p <venv 父目录> && python3 -m venv <venv_path> && <venv_path>/bin/pip install "mlx-whisper==0.4.3"` | PyPI（或清华镜像） | 实测约 760MB |
| Whisper Small | 首次转写时自动拉取（已缓存则复用并核验 revision） | `mlx-community/whisper-small-mlx` | ~500MB |
| Whisper Turbo | 精转时自动拉取（已缓存则复用并核验 revision） | `mlx-community/whisper-large-v3-turbo` | ~1.6GB |

`<venv_path>` 取 `analyzer-config.yaml` 的 `runtime.venv_path`（全机共享，不在产物目录内）。安装后把实际版本（macOS/架构、Python、FFmpeg、mlx-whisper、MLX、venv 绝对路径）写入 `execution-log.txt`。

版本固定：`mlx-whisper==0.4.3`。

## 五、阶段 2：音轨检查与提取

1. FFprobe 记录：总时长、全部音轨（索引/默认标记/编码/采样率/声道数/各轨时长）→ `source-info.json`
2. **音轨角色判定（多轨时强制，禁止仅按 default/顺序选轨）**：
   - 对每条音轨导出 16k 单声道副本，做**全片逐块（1s）能量剖面**，并对开头/结尾各 60s 做 Small 转写抽查
   - 按能量互补性与抽查内容判定各轨角色：
     - **分轨模式**：一轨基本只含面试官/系统声、另一轨基本只含候选人麦克风（同一时间窗口能量互补，如系统轨 64–137s 逐块全静音、麦克风轨同窗口连续语音）→ 双轨分别导出、分别转写、按时间戳合并
     - **冗余轨**：多轨转写内容重复 / 能量相关（相关系数 ≈ 1.0）→ 取一条
     - **无法判定** → 报用户，不自动选
   - 首次执行教训（多音轨实战场景）：录屏以「系统声音 + 麦克风」分双轨保存，但两条音轨 default 标记均为 true，不可作为选轨依据；按第一轨处理导致候选人整段缺失、被误判为「候选未作答」。**default 标记不参与选轨决策**
3. 导出方式：分轨模式每轨一个 `audio-source-track<N>.flac` + `audio-asr-track<N>.flac`（`-map 0:a:<stream_index> -ac 1 -ar 16000 -c:a flac`，N 取音轨序号）；单轨模式沿用 `audio-source.flac` / `audio-asr.flac`
4. **声道独立性自动判定**（Python/numpy，禁用 ffmpeg xcorrelate——那是视频滤镜）：
   - 解码为双通道数组，算左右相关系数与差异能量占比
   - 相关系数 ≈ 1.0 → 单声道复制，无需左右分轨，说话人标注回退 A/B
   - 明显独立 → 额外导出 `audio-left.flac` / `audio-right.flac`，说话人可结合声道来源标注
5. 生成 `audio-asr.flac`（`-ac 1 -ar 16000 -c:a flac`；分轨模式为各轨 `audio-asr-track<N>.flac`）
6. 验收：非空、`ffmpeg -v error -f null -` 完整解码通过、时长与视频差 < 2s；短超 5s 记警告不判失败

## 六、阶段 3：Whisper Small 全量粗转

固定参数：

```bash
HF_ENDPOINT=<预检决策> NO_PROXY=<预检决策> <venv_path>/bin/mlx_whisper audio-asr.flac \
  --model mlx-community/whisper-small-mlx \
  --language zh --task transcribe \
  --output-format all --output-dir <OUT> --output-name transcript-full \
  --initial-prompt "<专业词表>" \
  --verbose False
```

- `<venv_path>` = `analyzer-config.yaml` 的 `runtime.venv_path`（共享 venv，全机一个）
- 片段级时间戳（默认），不启用逐词，不翻译，不润色，不补写
- > 3 小时按 30 分钟逻辑区间 + 5 秒重叠处理，逐区间更新 state
- **必须检查进程真实退出码**（后台任务若接了管道 `tail`，`$?` 是管道末端的——用 `echo "EXIT_CODE=$?"` 直接跟在命令后，或不用管道）
- 首次下载后把模型 revision 写入日志；恢复执行复用同一 revision

### 专业词表（initial-prompt，按面试方向在配置中调整）

前端方向（当前）：`AI Coding, Claude Code, Agent, Planner, Reviewer, Hooks, Skills, Subagent, React, SSE, RAG, Node.js, TypeScript, Webpack, Vite`

## 七、阶段 3.5：转写病理检测与定向修复（新增，自动执行）

粗转完成后立即跑检测，全部为确定性规则（由执行引擎按以下逻辑实现，不要求预先存在脚本文件；实现逻辑如下）：

**静音区幻觉**（固定实现：FFmpeg 解码 + NumPy，禁止引入 soundfile 等新依赖）：
1. 解码：`ffmpeg -nostdin -v error -i audio-asr.flac -f f32le -ac 1 -ar 16000 -` 输出单通道 float32 原始 PCM，用共享 venv 的 Python 读入字节并 `numpy.frombuffer` 转为数组（`audio-asr.flac` 本就是 16kHz 单声道，无重采样）
2. 对每个转写片段的 `[start, end]` 区间，计算 RMS（均方根）：`sqrt(mean(segment**2))`
3. 若 RMS < `silence_rms_threshold`，标记为静音区幻觉
4. 窗口大小 `silence_energy_window_ms` 仅用于计算分区（若按整体区间计算 RMS 则忽略；默认按整体区间计算）

**重复循环**：扫描 `transcript-full.json` 的 segments，若连续 `loop_repeat_min` 段文本完全一致且长度 ≥ `loop_text_min_chars`，记录循环起点。

**时间戳断档**：计算相邻段间隔（next.start - current.end），若 > `timestamp_gap_seconds` 秒且音频该处 RMS ≥ `silence_rms_threshold`，标记可疑区间。

**常见中文幻觉词**：用字符串匹配（不区分大小写、简繁），正则 `字幕|谢谢观看|请不吝点赞|订阅|关注|点赞|投币`，定位命中片段时间点。


| 病理 | 检测方法 | 处置 |
|---|---|---|
| 静音区幻觉 | 音频能量（RMS）低于 `silence_rms_threshold` 的区间内出现的文本 | 标记排除，不重转；阈值与窗口见 `analyzer-config.yaml` |
| 重复循环 | 连续 N 段（N≥`loop_repeat_min`）文本完全相同且长度 > `loop_text_min_chars` 字符；**判定时叠加 RMS 验证**——循环区间 RMS < `silence_rms_threshold` → 静音幻觉（排除），≥ 阈值 → 疑似真口吃（记录并报告用户，不自行删除） | 记录坏区间起点；阈值见 `analyzer-config.yaml` |
| 时间戳断档 | 段间间隔 > `timestamp_gap_seconds` 秒且音频该处非静音 | 标记可疑区间；阈值见 `analyzer-config.yaml` |
| 常见中文幻觉词 | "字幕/谢谢观看/请不吝点赞/订阅" 等 | 定位时间点 |

**循环幻觉修复流程（Turbo 阶段同样适用）**：

1. 取坏区间起点前 10 秒作为重转起点
2. 用相同模型 + `--condition-on-previous-text False` + `--clip-timestamps "<起点>,<终点>"` 只重转该区间
3. 合并时按时间戳切分：重转结果覆盖坏区间，边界 ±3 秒重叠区去重
4. 修复后重跑病理检测，直至无循环

**合并规则（确定性，修复窗口 = `[修复起点 - 3s, 修复终点 + 3s]`）**：

1. 合并产物固定命名 `transcript-full-merged.json`（Small 修复合并）；Turbo 修复合并为 `transcript-turbo-merged.json`。原 `transcript-full.json` 已验收，禁止覆盖。
2. 落在修复窗口内的原段全部丢弃，由修复段替换。
3. 修复段**整段保留，不截断、不因跨界丢弃**：凡 `start` 落在修复窗口内的修复段，即使 `end` 超出 `修复终点 + 3s`（如修复 20–1440s 但末段到 1461.5s），仍保留完整段。理由：Whisper 段边界落在短语/停顿处，截断会产生残句；跨界部分本就是同一段音频的重新转写，覆盖原内容无信息损失。
4. **修复段优先**：修复段整段跨度内覆盖到的窗口外原段同样丢弃，不产生同音频双写。
5. 窗口外且未被修复段覆盖的原段原样保留。
6. 合并结果按时间戳升序重排，输出到合并产物文件；随后跑病理检测复检。

> 首次执行教训：Turbo 在 8 分钟后陷入"嗯"×100 循环，丢失 80% 内容。`--condition-on-previous-text False`（连字符 CLI 参数）是有效修复且只重转坏区间，代价极小。

## 八、阶段 4：问题索引（密度聚类版）

> 原方案的"命中区间 ±90s 扩展后合并"在技术面场景失效（关键词全程密集，合并成 98.5% 一个大区间）。改为：

### 确定性脚本（不调 LLM）产出三张视图

1. **主题簇视图**（默认呈现）：
   - 主题关键词分两组，完整词表见 `analyzer-config.yaml` 的 `indexing.ai_coding_keywords` 与 `indexing.project_keywords`
   - 匹配规则：ASCII 词按词边界 + 不区分大小写匹配，中文按子串匹配（避免 "AI" 命中英文子串导致覆盖虚高）
   - 命中段按"间隔 < 180s 归为一簇"聚类，**不做 ±90s 扩展**
   - 输出每簇的起止时间、命中段数、时长
2. **问句事件视图**：问句表达（`indexing.question_patterns`）逐条列出：时间 + 命中词 + 粗转文本
3. **必须包含区间**：面试开头（首个语音起 ±2 分钟）、反问环节（结尾 1/3 区域搜索 `indexing.reverse_question_patterns`）、结束前 5 分钟

### 问句识别扩展（覆盖不含 question_patterns 的问句）

> 首次执行教训：只靠 `question_patterns`（为什么/怎么/如何/有没有/介绍一下/具体说说）会漏掉「有遇到过……卡顿吗」这类明显问句，导致回答窗口错误套到下一问句上、说话人错归属。问句识别必须扩展：

- 任一 segment 满足以下**任一条件**即记为问句候选，与原 pattern 命中合并、按时间排序去重：
  - **句末疑问助词**：以 `吗|呢|吧|嘛|？|?` 结尾（如 264.52s「有遇到过……卡顿吗」为实测漏检案例）
  - **疑问代词/副词**：`哪|什么|啥|谁|为什么|怎么|如何|为啥|多少|多久`
  - **确认/选择句式**：`是吧|对吧|是吗|是不是|有没有|还是|或者说`
  - **反问/连续追问引导**：以 `那为什么|那你们|那怎么|那你` 开头
- **排除规则（防止候选回答被误判为问句）**：
  - 命中静音幻觉检测的段（RMS < `silence_rms_threshold`）先剔除
  - 短回应词（`嗯|对|好|OK|对对对|大概理解` 等 ≤2 词）不算问句
  - 以 `对|因为|其实|就是说|它是|这个` 开头的解释性段不算问句（疑问词在句首时除外）
- **回答窗口重定义**：候选回答窗口 = `问句 i 结束时间 → 下一问句 i+1 开始时间`，问句列表为**全部**识别出的问句（含扩展规则捕获的），不再只用 pattern 命中子集。窗口 < 3s 视为连续追问，不单独处理
- **无法归属的段**（既非明确问句也非明确应答）：保留 `[说话人不确定]`，禁止臆断

### 覆盖率决策（自动）

- 主题簇总覆盖 ≤ 40%：自动按簇精转
- 覆盖 > 40%：**停止，给用户三选项菜单**（附各选项预计精转时长）：
  - a. 全程精转（需明确批准偏离"禁止全量 Turbo"条款）
  - b. 只精转高密度簇（命中段数 top 簇）
  - c. 用户手选区间（读 question-index.md）

## 九、阶段 5：Turbo 精转

```bash
HF_ENDPOINT=<预检决策> NO_PROXY=<预检决策> <venv_path>/bin/mlx_whisper audio-asr.flac \
  --model mlx-community/whisper-large-v3-turbo \
  --language zh --task transcribe \
  --output-format json --output-dir <OUT> --output-name transcript-turbo-clip-<n> \
  --word-timestamps True \
  --clip-timestamps "<区间起点>,<区间终点>" \
  --initial-prompt "<专业词表>" \
  --condition-on-previous-text False \
  --verbose False
```

- **默认加 `--condition-on-previous-text False`**（防循环；实测对质量无负面影响）
- 只处理用户确认或规则选中的区间；禁止对完整音频运行（除非用户批准选项 a）
- **每个区间必须单独一条命令、单个 `--clip-timestamps "<起点>,<终点>"`**。mlx-whisper 0.4.3 的多区间 `--clip-timestamps "a,b,c,d,..."` 有 bug：`seek` 变量跨区间不重置，会从首个区间起点**连续转录**到末区间终点，把间隔区全部转录（实测 `0,170,...,3269.26,3569.26` 产出 28.58–3569.24s 全程）。单区间正常（Small 修复 20,1440 产出 20.0–1461.5 已验证）
- 单命令产物命名 `transcript-turbo-clip-<n>.json`（n 从 1 递增，按选定区间顺序）；全部区间完成后合并为 `transcript-turbo-merged.json`，合并规则沿用阶段 3.5 的确定性规则（修复段整段保留、修复优先、窗口内原段丢弃、按时间戳升序）
- **Turbo 验收判据**：拒绝「某段完整落在所有 `[区间起点-3s, 区间终点+3s]` 窗口之外」的产物（即连续转录的间隔区特征）；允许单个片段因短语延续轻微越界（跨 `区间终点+3s` 不超过约 30s，视为正常 overshoot 而非违规）
- 精转后立即跑阶段 3.5 的病理检测
- **时间戳绝对性校验**：clip 起点后取一段文本，在粗转中找相同内容比对时间；偏差 ≈ 0 → 绝对时间戳；偏差 ≈ clip 起点 → 相对时间戳需加偏移

**Turbo 修复与二次合并（复检出循环时）**：

- 修复命令与 clip 相同参数（含 `--word-timestamps True`），`--clip-timestamps "<循环起点前10秒>,<循环终点>"` 单区间（clip 值用精确值，如 `87.58,158.98`）
- 修复片段文件名一律用**整数边界**：`transcript-turbo-repair-<round(起点)>-<round(终点)>.json`（如 `transcript-turbo-repair-88-159.json`）。mlx-whisper 把 `--output-name` 末尾的 `.NN` 当扩展名替换（实测 `...-87.58-158.98` 产出 `...-87.58-158.json`），文件名含小数必被改写；`--clip-timestamps` 不受影响、仍用精确值。Small 修复命名 `transcript-small-repair-<起点>-<终点>.json` 同规则（整数边界）
- 二次合并产物 `transcript-turbo-merged-v<N>.json`（N 从 2 递增），以当前已验收的 merged 为底，替换循环窗口，合并规则不变；**永不覆盖任何已验收版本**
- 若修复命令产出仍含循环（同参数在窄窗口重转仍复现）→ 停止并报告用户，不自行换参（如调 temperature）或接受含循环产物

### transcript-key.md 整理规则

- 逐题结构：问题主题 / 时间 / 面试官原话 / 候选人原话 / 追问 / 客观现场信号；每题分「面试官：」与「候选人：」两块，参考已验收的标准 transcript-key.md 格式
- 说话人标注：**分轨模式下按音轨直接归属**（面试官轨 → 面试官，候选人轨 → 候选人），不依赖语气猜测；同轨内仍按下述 A/B 规则与孤回应规则处理（如候选人轨内拾入的面试官近场声）
- 说话人标注（无声道分离/单轨时**强制执行，禁止整稿标不确定**）：
  1. 先标 A/B：命中 `question_patterns` 的段及其直接延续 → A；紧随 A 之后的非问句应答段 → B；孤立短回应（嗯/对/好/OK 等 1–2 词）→ `[说话人不确定]`
  2. 升级为问答身份：A → 面试官，B → 候选人（若语义明显相反则互换，如候选人在自我介绍）
  3. 面试官块只放问句原话，候选人块只放应答原话，全部带时间戳
  4. 仅当某段整段无问答线索时才保留 `[说话人不确定]`
- 听不清标 `[听不清]`，术语不确定标 `[术语不确定：候选词]`，一律不补写
- **ASR 术语误识别对照表**放文件头部（如 reg→RAG、Cloud Code→Claude Code、上约文→上下文），原话保持转写原样，括号内推断纠正仅作标注
- 引用原话必须带时间戳

## 十、阶段 6：质量校验

抽检：开头/中间/结尾各 60 秒 + 全部关键问答，与 Small 粗转交叉比对语义一致性。

检查项：时间戳连续、重叠区去重、静音幻觉、重复循环、技术词误识别、擅自补全。发现错误只重转对应区间（走阶段 3.5 修复流程），不重跑全量。

### 关键问答覆盖不足时的补选区规则

- **幻觉段先排除**：合并产物必须跑阶段 3.5 的「常见中文幻觉词」检测（正则 `字幕|谢谢观看|请不吝点赞|订阅|关注|点赞|投币`），命中的段标记排除；排除段不进入 transcript-key.md、不参与覆盖计数。实测 Turbo 输出中「请不吝点赞 订阅 转发 打赏支持明镜与点点栏目」出现多次，属已知幻觉模式
- **覆盖判据**：问句事件已覆盖 ⟺ 事件时间点 **±20s** 内存在**有效** Turbo 分段（有效 = 未标记排除的段）。理由：Small 与 Turbo 为不同模型，分段时间戳漂移实测最大约 16s（如事件 1284.06s 对应 Turbo 段 1300.58s），±20s 是实测漂移的确定性上界；不用 ±3s 等小容差，否则受漂移误伤
- **补选区生成**：未覆盖问句按相邻间隔 ≤ 120s 聚类；每簇区间 = `[首事件时间 - 10s, 末事件时间 + 60s]`；重叠簇合并
- **覆盖率复核**：补选后与现有 Turbo 覆盖合并计算总覆盖率。≤ 40% → 自动逐区间单命令精转；> 40% → 走阶段 4 的三选一用户菜单（全程 / 高密度簇 / 手选），不自动继续
- 新增区间沿用单命令单区间 `--clip-timestamps`（避免 0.4.3 多区间 bug），产物 `transcript-turbo-clip-<n>.json`（n 续增），与既有 clip 合并为 `transcript-turbo-merged-v<N>.json`（N 递增，不覆盖已验收版本）

### 回答缺失区处理规则（候选答案缺失时不阻塞，按确定性流程处理）

> 首次执行教训（已验证）：回答窗口内「有语音」≠「候选人在回答」。实测：
> - **静音判定必须逐块（0.5–1s），禁止用窗口平均 RMS**。Q1 自介窗口平均 RMS=0.0157 看似有语音，实际 63s 后逐块全 < 阈值，平均值是开头面试官提问拉高的；窗口平均会系统性误判长窗口
> - **窗口内语音默认先视为面试官继续追问，转出文本呈答句语气才归候选人**。Q4/Q6/Q12/Q13/Q14/Q15/Q19/Q20 窗口内语音逐段重转后全部是面试官追问（如「就假设你们那个做的…怎么去做消费的」「是会有这种顺序依赖吗」），候选人在这些窗口未出声
> - 曾把 921–935、1240–1262 按窗口 RMS>0.005 误判为「有语音但两模型均漏」并重转，实测 921–924 是面试官问题结尾、1240–1262 基本静音 → **有语音必须先窄区间重转确认内容与说话人，不能仅凭 RMS 认定存在候选回答**
> - **单轨静音可能不是候选人未作答，而是没选对音轨（多音轨实战根因）**：上述 Q1 自介「63s 后逐块全静音」等判定均只对已选系统声轨成立；录屏另有候选人麦克风轨，同窗口连续 73s 语音即候选人完整自我介绍。**回答缺失大面积出现时必须先回查其他音轨，把单轨静音解释为未作答是最危险的路径**

- **音轨完整性前置校验（候选缺失时强制回查）**：分轨模式下候选回答一律取自候选人轨；若候选人轨转写后某题仍无候选文本，才进入下方逐块判定。**单轨模式下若超过 1/3 回答窗口无候选文本，必须先回查其他音轨是否存在候选人语音（逐块能量剖面 + 窄区间转写抽查），禁止直接标注 `[候选未作答]`**
- **回答窗口**：`问句 i 结束时间` 到 `下一问句 i+1 开始时间`，问句列表为**全部**识别出的问句（含阶段 8 问句识别扩展捕获的，非仅 pattern 命中）；窗口 < 3s 视为连续追问，不单独处理
- **候选回答来源优先级（不编造）**：
  0. **分轨模式候选人轨（audio-asr-track2.flac 等）对应窗口段**：直接作为候选回答，说话人标候选人；该轨转写独立于面试官轨，不依赖语气猜测
  1. **Turbo 合并产物已有有效段**：直接使用，走说话人标注规则
  2. **transcript-full-merged.json 补**：回答窗口内 Small 有效段作为该题候选回答来源。质量以文件头「ASR 术语误识别对照表」兜底
- **所有来源统一过静音区幻觉检测**：候选回答（Turbo 或 Small 段）对应的音频区间必须**逐块 RMS ≥ `silence_rms_threshold`**，低于阈值的文本一律视为静音幻觉排除，不得进入 transcript-key.md。实测 1878s「我们现在就来做一个业务」循环段 RMS=0.002 落在静音区，即此类反例
- **窗口内剩余语音的判定（Turbo/Small 均无有效段时）**：把窗口内逐块 RMS ≥ 阈值的**连续语音子区间**（0.5s 粒度）逐一窄区间重转 `--clip-timestamps "<子区间起点-1s>,<子区间终点+1s>"`（单区间，与 clip 同参数），产物 `transcript-turbo-repair-<round(起点)>-<round(终点)>.json`。用重转**文本内容**判定说话人：
  - 呈问句/追问语气（`怎么|为什么|那你们|是不是|对吧|就假设|还是` 引导或疑问助词结尾）→ **面试官追问**，补入该题面试官块，不当作候选回答
  - 呈答句语气（陈述、确认、解释，非疑问）→ **候选回答**，补入候选块
- **窗口内无任何语音子区间**（逐块全 < 阈值）：标注 `[该处音频无语音，候选未作答]`，不补、不重转
- **语音子区间重转仍为空** → 标注 `[该处语音听不清，未能转写]`，接受并继续，不无限重试、不自行换参
- **回答覆盖校验（新增必过检查项）**：每个问句必须满足「Turbo 有效段 或 Small 补 或 重转成功 或 明确标注未作答/听不清」之一，否则判定质量不合格，禁止以缺失回答通过校验

## 十一、阶段 7：逐题分析（外部模型，可插拔）

分析器三种模式，由用户选择：

| 模式 | 说明 |
|---|---|
| `codex` | 生成 `codex-analysis-prompt.md`，用户手动粘给 Codex 执行 |
| `api` | 用户提供模型 API（按方案原定 gpt-5.4-mini / reasoning effort low） |
| `self` | 当前会话模型直接分析 |

**输入约束**：分析模型只允许读 `transcript-key.md`；按完整问答边界拆分，单主题超 8000 Token 继续拆；禁止读原视频/音频/完整转写。

**分析顺序**：AI Coding 工作流 → 项目经历 → 面试官现场信号 → 综合判断（只输入前三步结论与必要原话）。

**每题七项固定结构**：考察目标 / 覆盖内容 / 缺失与风险 / 客观信号 / 失分判定（明确失分/隐性失分/无明显问题）/ 更好的回答结构 / 影响与置信度。

**禁止**：没追问≠答得好；候选人主观感受≠面试官评价；单题≠淘汰原因；无证据不猜态度；不虚构细节。所有结论区分**事实**（原话+时间戳）/ **推断**（注明依据）/ **无法判断**（说明缺什么证据）。
